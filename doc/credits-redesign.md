# Credits 重构：站内唯一计价单位

状态：**P1-P5 已实施** · 2026-08-08

实施记录见各期 commit（feat(credits): P1..P4 与本文档的契约同步）。
下方「分期」表已按实际落地情况标注。

## 1. 目标

把「钱包余额 / AI 额度 / 创作者收益」三套并行的计价口径收成一个：**Credits**。

- 充值即得 Credits，**没有「再分配一次」的环节**；
- Credits 直接用于 AI、购买 Skill / 插件 / 功能解锁；
- 创作者分成**自动**入 Credits，不再人工打款。

非目标：本轮不做提现。分成一律以 Credits 结算，不出金——这是刻意的合规取舍，
避开代付通道、反洗钱与个税代扣。

## 2. 现状（2026-08-08 代码核查）

| 事项 | 现状 |
|---|---|
| 创作者能否自己定价 | **能**。投稿表单有价格字段（元，0 = 免费，上限 ¥1999）→ `skills-store.priceCents` |
| 七三分成算得对不对 | **对且自动**。`fulfillPurchase` 在同一事务写 `purchases` + `entitlements` + `creator_earnings`，创作者 70% 向下取整、余数归平台，两者之和恒等于总价 |
| 分成怎么到创作者手里 | **人工**。`creator_earnings` 只记账，admin「收益结算」需线下转账后填凭证说明再标记 |
| 广场购买走不走钱包 | **不走**。一律微信扫码直付，不写 `wallet_ledger` |
| AI 额度怎么来 | 用户在账户页手动「从余额分配」→ 扣 `wallet_ledger(ai_alloc)` → `createKey/patchKeyLimit` 提额 |
| 线上付费条目 | **0 条**（28 条 Skill 全免费）→ `creator_earnings` 为空，**无历史负债要迁移** |

最后一行是本次重构最大的有利条件：分成机器从未真正跑过，改口径不用处理存量。

## 3. 核心模型

### 3.1 一个单位，两种批次

用户看到的永远是**一个** Credits 余额。内部按批次（lot）记账，两类属性不同：

| 批次 | 来源 | 有效期 | 可退现 | 理由 |
|---|---|---|---|---|
| `topup` 充值 Credits | 微信充值 | **不过期** | 可（原路退回） | 用户真金白银付进来的钱。设有效期触碰《单用途商业预付卡管理办法（试行）》第十八条「记名卡不得设有效期」，且余额过期作废在《消法》第二十六条、《民法典》第四百九十七条下属限制消费者主要权利，实务中被认定无效的不少 |
| `reward` 奖励 Credits | 创作分成、活动赠送、兑换码 | **入账起 24 个月** | 否 | 平台无偿发放，是我们账上的负债。设有效期是通行做法（积分/里程），可封住负债无限期展期 |

**消费顺序：`reward` 优先 → `topup` 其次；同类先到期者先扣。**
先烧掉会过期的负债，用户也不吃亏。

### 3.2 为什么不能合成一个池子

若两类混为一笔余额，创作者可以赚 1000 Credits 再申请「退未消耗余额」——就是绕个弯的提现，
本次重构的合规目的直接落空。分批次存储让「奖励不可提现」是**数据层的事实**，
而不只是条款里的一句话。

## 4. AI：取消用户侧 allocate

### 4.1 约束

桌面端持 provisioned key **直连** OpenRouter，我们不在请求路径上，**无法按次原子扣 Credits**。
因此「取消 allocate」只能取消用户看到的那一步，底层 provisioning 必须保留。

（评估过「代理全部 AI 请求」以实现精确扣费：我们要进热路径，承担延迟、可用性与流量成本。
不采纳。）

### 4.2 预留（reservation）模型

把 OpenRouter key 的 `limit` 定义为**已预留给 AI 的 Credits**：

```
可用 Credits = 余额 − 预留
预留        = 折算回人民币的 (limitUsd − usageUsd)
```

- **自动提额**：余额增加（充值 / 分成入账）时，把新增部分预留给 AI，`patchKeyLimit(旧 + 增量)`。
  用户充完值 AI 立即可用，全程无「分配」字样。
- **释放预留**：用 Credits 买广场条目而可用不足时，先下调 key limit 释放预留。
  **只能释放未被 AI 花掉的部分**——已消耗的额度收不回。
- **用量回抄**：定期（及账户页读取时）`getKey` 拉 usage，折算人民币后写一行 `ai_usage` 扣减，
  同额减少预留。

沿用现有两条硬规则，不许回退：
- OpenRouter `limit` 是**累计口径**，提额必须「读远端旧值 + 增量」，绝不覆盖写；
- `patchKeyLimit` 抛错后必须 `getKey` 实查判定是否已生效再决定退款，不能直接退
  （否则用户既拿到额度又拿回 Credits）。

## 5. 广场购买改走 Credits

现状是微信扫码直付、不碰钱包。改造后：

1. **有足够 Credits** → 直接扣 Credits 成交（无支付跳转，体验最好）；
2. **不足** → 走微信充值补足后再扣，或直接扫码直付（保留现有路径作兜底）。

扣减必须与 `purchases` / `entitlements` / 创作者入账在**同一事务**内完成，沿用
`fulfillPurchase` 现有的幂等口径（`idempotencyKey` 唯一索引 + 重复履约不重复分成）。

## 6. 创作者分成

`creator_earnings` 保留为收益明细表，但结算方式改变：

- 履约事务内直接给创作者写一笔 `reward` 批次的 Credits 入账，`settledAt` 立即置位；
- admin「收益结算」面板从「人工打款 + 填凭证」退化为**只读对账视图**；
- 七三比例、向下取整、余数归平台的口径**不变**。

这是「自动分成」得以成立的关键：分钱必须人工（银行/代付/个税），分 Credits 可以在
支付回调那个事务里一并写完。

## 7. 契约与条款的连带变更

**桌面端契约**（`doc/desktop-contract.md` 与桌面仓 `LicenseService` / 账户页需同步）：

- `GET /api/account/ai-usage`：新增可用/预留 Credits 字段，`hasKey=false` 不再意味着「没分配过」；
- `POST /api/account/ai-key`：不再返回 `409 no_allocation`——有 Credits 即可签发；
- `GET /api/account/wallet`：余额语义改为 Credits，明细带批次与到期日。

**条款**（今天刚上线，必须同步改，否则文本与实现不符）：

- 服务条款第六条：删「由我们结算打款」，改为「以 Credits 结算，不可提现」；
- 服务条款第七条：区分充值 Credits（可退）与奖励 Credits（不可退、24 个月有效期），
  并把有效期写进需显著提示的条款。

## 9. 未决

- **到期提醒怎么发**：站内还是邮件？目前没有事务邮件通道。账户页已显示最近一笔的
  到期日期，但没有主动提醒。
- **桌面端尚未内置「用 Credits 买」**：`POST /api/account/purchase` 已可用，但桌面端
  命中 402 时仍然是跳官网购买页。接进去是纯前端工作，没有契约风险。
- **奖励 Credits 到期作废的会计处理**：冲回负债确认收入的时点，需财务口径确认。
- **创作者互购的循环**：A 用奖励 Credits 买 B 的条目，B 再拿 70% 奖励 Credits。
  经济上收敛（每轮 30% 沉淀给平台），但负债在多个账户间流转，对账要认得出这条链。
