# Browser workbench AI v1

The Web IDE is anonymous for local editing and export. AI requires the website's host-only session cookie and existing spendable Credits or Pro allowance. Desktop trial turns alone are not accepted because their current completion-only counter cannot reserve an upstream call. No new grant or Skill AI subsidy is introduced. `WEB_AI_ENABLED=1` and an existing server `OPENROUTER_API_KEY` (or `data/ai-config.json` key) enable the feature after acceptance.

## Browser contract

- `GET /api/web/capabilities?lang=zh|en`: `authenticated`, `aiEnabled`, `reason`, `model`, `limits`, `currency`, `maxChargeCents`, `webTrialSupported:false`, `loginUrl`. Authenticated responses also include `spendableCents`, `trial`, and `activeRequest:{requestId,state}|null`. Show the maximum reservation and trial limitation before the first paid action. `trial` is informational, not eligibility. Navigate the top-level window to the returned same-host account URL; the existing login form returns to `/web/?lang=...`.
- `POST /api/web/chat`: JSON `{requestId:UUID,language:'zh'|'en',mode:'chat'|'rewrite',message,history:[{role:'user'|'assistant',content}],document:{id:UUID,version:nonnegativeInteger,name,text},selection?:{text}}`. Cookies and an exact allowed same-host Origin are required. No bearer key is issued. Unknown account/model/provider fields are rejected. The request body is bounded to 96 KB and normalized context to 48 KB UTF-8; history at most 10 messages, instruction 4,000 characters, selection 6,000 characters. Rewrite selection must have exactly one literal occurrence in the snapshot.
- SSE: `start:{requestId}`, `delta:{text}`, `proposal:{requestId,fileId,version,original,replacement,explanation}`, `usage`, `error:{code,message}`, `done:{requestId}`. Rewrite emits a proposal only after complete strict JSON validation. It never executes tools or modifies documents server-side. The client must recheck file/version/literal text before applying. Invalid proposals still incur verified generation costs.
- `GET /api/web/requests/:requestId?lang=...`: owner-only receipt. Fields: `requestId,state,model,reservedCents,currency,updatedAt`, optional `errorCode`; verified provider costs appear as `costUsd` even if they exceeded the cap and await incident review; settled receipts have `chargedCents,ledgerId`; released/refunded receipts have `chargedCents:0` but no invented `costUsd`. `usage` uses this receipt shape.
- Errors use JSON `{error:{code,message}}` before streaming. Status 401 requires login, 402 means insufficient available funds, 409 means busy/duplicate/payload conflict, 413 overlarge context, 429 rate limit, 503 unavailable or reconciliation paused. Duplicate requests never rerun the provider. Read their receipt instead. Document text and AI output are never persisted on the server, so a lost completed result cannot be replayed; a new generation is a new paid action.

## Funding and bounded provider request

The server fixes `qwen/qwen3-235b-a22b-2507`, a non-reasoning text model. Public model metadata verified 2026-10-13. Provider caps are $1/million input tokens and $2/million output tokens, no request fee, and no tools/images/plugins. Provider fallback is enabled within that one fixed model; every eligible endpoint remains subject to the same price caps, `require_parameters:true`, and `data_collection:deny`. No `models` fallback list or alternate model router is sent, and the application never retries a completion. Maximum output is 2,048 tokens and 16,000 characters. Byte-based context bound plus 4,096 framing tokens reserves at most $0.056192 upstream per request. Local minor-unit reservation is `ceil(maxUSD × capturedFX × capturedMargin × 100)`. Actual final reported USD cost uses the same captured FX/margin. Routing fails when no provider meets the cap.

`BEGIN IMMEDIATE` atomically checks the payload-bound request ID, per-user/global concurrency, rate limits, and spends the reservation from existing `ServiceFunding`. One active request per user; eight globally; six/minute and 80/day. Settlement atomically refunds the reservation and re-debits verified actual cost against its original subscription period/week and authorization time, including credits that expired while running. Unused funds return to original lots, preserving reward/topup semantics. It never bills above the displayed reservation.

Existing desktop direct-provider keys are synchronized after reservation before Web submission and after settlement. Failed/insufficient cap synchronization stops Web submission. Legacy desktop in-flight usage has the existing eventual-settlement exposure; this change does not claim to eliminate it or alter its policy.

## Interruptions and recovery

Mark `submitted` durably before the network call. No network/completion retry follows an uncertain delivery. Browser cancellation detaches the client while the bounded server request continues to obtain usage and settle. Only definite provider rejections or pre-submission failures release immediately. A rejected request logs only its safe HTTP status and request UUID internally; raw provider responses are discarded. Released receipts omit unknown `costUsd` instead of fabricating zero. Stream truncation does not make partial `usage.cost` authoritative.

Unknown usage is `usage_pending`; the server can query the provider generation receipt without rerunning generation. Status polling attempts this at most every 30 seconds. After 15 minutes from creation, an unresolved status query returns the original reservation and records `refunded_pending`, then globally pauses new Web AI. There are at most eight already-active requests. This is a finite incident recovery mechanism, not free product usage. No retroactive debit follows an incident refund. If generation ID was never received, do not fabricate it or replay the call.

The browser must retain the request ID and offer **Check request status** after stop/network error and for `activeRequest`. The operator can also run, from the server checkout:

```sh
node_modules/.bin/tsx --tsconfig tsconfig.json scripts/web-ai-reconcile.mts list
node_modules/.bin/tsx --tsconfig tsconfig.json scripts/web-ai-reconcile.mts reconcile USER_ID REQUEST_UUID
```

After investigating provider logs, recorded costs/cap violations and the cause, an authorized operator may acknowledge an already-refunded incident with an incident reference:

```sh
node_modules/.bin/tsx --tsconfig tsconfig.json scripts/web-ai-reconcile.mts close-refunded-incident USER_ID REQUEST_UUID INCIDENT_REFERENCE
```

This writes `admin_audit`, preserves unknown cost as unknown, and never changes user balance. New calls remain paused until all such incidents are closed. There is no public admin bypass. Unvisited requests can be reconciled with the same operator command; no recurring job is added by this change.

Account deletion blocks `reserved`, `submitted`, and `usage_pending` requests using the existing `has_pending_allocation` result. The existing transaction recheck also catches a reservation created while remote key revocation is awaiting a response. `settled`, `released`, and `refunded_pending` records receive the same deterministic user tombstone as their ledger records, retaining receipt fields and accounting links. An incident refund cannot be retrospectively charged and does not itself block deletion; its retained `refunded_pending` record still pauses new Web AI requests globally until an operator closes it using the tombstone user ID.

## Validation

`npm run test:web-api` runs synthetic users, sessions, provider responses and a fresh temporary SQLite DB, never production records or live providers. The optional `scripts/web-ai-live-smoke.mts --dry-run` prints the real-provider plan without reading credentials. Actual execution requires separate budget approval: two calls maximum, total upstream ceiling $0.112384. The approved server-only procedure reads the existing server key in-process, creates a private temporary synthetic DB/user/session, prints only verified receipt metadata, and cleans up. No real-provider success is claimed until that run passes.

Routing semantics checked against official [provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) and separate [model fallbacks](https://openrouter.ai/docs/guides/routing/model-fallbacks) documentation on 2026-10-13. Provider availability is not guaranteed if every endpoint is rate-limited or excluded by price/privacy/parameter constraints.

Sources: [OpenRouter provider price caps](https://openrouter.ai/docs/guides/routing/provider-selection#max-price), [generation usage receipt](https://openrouter.ai/docs/api/api-reference/generations/get-request-&-usage-metadata-for-a-generation). Existing funding primitives: `lib/credits.ts`, `lib/subscription.ts`; existing Skill policy remains in `lib/ai-usage.ts` unchanged.

## Direct document agent (additive contract, dev-board#1266)

`mode:'agent'` on the same POST endpoint enables native OpenRouter function calls. Existing `chat` and `rewrite` requests, prompts, SSE and price ceilings remain unchanged. Agent input additionally requires:

- `agentStep:0..3`; the last step uses `tool_choice:'none'` and rejects any returned tool.
- `agentContext:{runId,targets}` with editor-minted paragraph/boundary handles. `document` is the current snapshot and is not duplicated inside context. Handles carry no executable editor command.
- `agentHistory`: exactly `agentStep` assistant/tool pairs. The assistant contains one native `tool_calls` entry with JSON-string arguments; its following `role:'tool'` message has the matching `tool_call_id` and a JSON-string editor result. Only allowlisted tool schemas pass validation. Result `tool`, `runId`, and document ID must match. No system/developer roles are accepted.
- `agentBudget:{currency,perGenerationMaxChargeCents}` freezes the quoted ceiling for the client run. This is only a ceiling, never a replacement price. The server calculates the actual reservation itself. Step 0 requires the submitted quote to equal that current reservation exactly; both inflated and undersized quotes receive `price_changed` (409) before any run creation, debit or provider submission. Later steps retain the frozen quote and may proceed at a lower current reservation, but reject currency changes or a price above the original ceiling.

The shared `web-workbench/src/agent-contract.js` is the allowlist and validator for both server and browser: `doc_find_text`, `doc_read_tables`, and `doc_apply_edits`. Edits include literal replacement (empty replacement deletes), insertion, bounded character/paragraph formatting, small rectangular table creation, and writing an existing single cell. There is no arbitrary UNO/action/code/URL field, network tool, cross-document tool, server tool or plugin. Each generation may return at most one tool call; `doc_apply_edits` contains at most 12 operations. The browser limits a run to 24 edits and four generations, with a ten-minute deadline. The four-generation and ten-minute limits are also enforced persistently by the server. Existing per-generation account/global concurrency and rate limits still apply. The browser additionally enforces the 24-edit native execution ceiling.

The provider parser accumulates `delta.tool_calls` fragments by index, including split arguments and UTF-8 network chunks. Only complete `finish_reason:'tool_calls'` output ending in `[DONE]`, validated against the allowlist, can be dispatched. Multiple, malformed, truncated or final-step calls never execute. Omit `parallel_tool_calls`: the public endpoint metadata for the fixed model does not currently list it, and `require_parameters:true` must remain enabled. Application validation enforces one call regardless.

After verified settlement, SSE emits `tool_calls:{requestId,fileId,version,calls,assistant}`. `calls` contains validated argument objects for execution; `assistant` retains the native JSON-string arguments for the next request's history. The browser revalidates, binds execution to its live run/file/revision, executes native operations, and reads back changes. It returns `{ok,tool,runId,document:{id,name,version},revision,saved,partial,verification,result,error?}`. A successful result must be `verification:'verified'` with no partial/error flag. Failures explicitly report known applied, failed, not-run or unknown operations. Model prose is never evidence of success. Results are bounded data, not instructions. Server result validation checks the strict envelope and bounded JSON payload; actual native verification is the editor's responsibility.

Each generation retains its own new `requestId`, one provider generation and existing reservation/settlement. An additive metadata-only `web_ai_agent_run` table enforces the run boundary without replacing any request ledger, automatically retrying a completion, or retrospectively charging a refunded receipt. The UI sums actual `chargedCents` across requests, rather than presenting a fictitious single charge. Unknown usage stops the client loop and withholds executable tools; existing receipt reconciliation and incident refund/pause remain in force for that request. Earlier settled generations remain charged. Unknown usage permanently stops that run, even if a later receipt reconciles the generation; start a new explicitly requested run for additional work. Disconnect stops dispatch and later generations; the already-submitted bounded provider generation still settles. A lost tool response is not replayed from the metadata-only receipt.

Agent requests have a 128,000-byte body ceiling. Their initial legacy document/instruction/history snapshot retains the 48,000-byte bound; context and each tool result are at most 24,000 bytes, and tool arguments at most 16,000 bytes. Before submission, the entire serialized provider `messages` plus fixed `tools` must fit 96,000 UTF-8 bytes; growing history is never silently truncated. At the unchanged price caps and 2,048 output tokens, the per-generation upstream ceiling is `((96000+4096)*1+2048*2)/1000000 = $0.104192`. Four generations have an upstream ceiling of $0.416768; displayed local ceiling is **four times each generation's rounded-up minor-unit reservation**, and actual totals sum each separately rounded settlement. `capabilities` adds `agentEnabled`, `agentReason`, and `agent:{limits,maxGenerations,maxChargeCents,maxRunChargeCents}` while retaining all legacy fields. Insufficient credit partway through a run leaves verified edits in place and reports unfinished work.

Validation extends `npm run test:web-api` with native fragmented tools, strict edit schemas, paired history, final-step tools disabled, invalid/parallel/truncated calls, unknown fees, client detachment, complete context bounds and frozen quotes. These are synthetic provider tests, not proof of real-model or native-editor correctness. Public model support is checked using the official [model endpoint metadata](https://openrouter.ai/api/v1/models/qwen/qwen3-235b-a22b-2507/endpoints) and [tool calling protocol](https://openrouter.ai/docs/guides/features/tool-calling); live model and native editing acceptance remain separate gates.

### Persistent run authorization

Migration 38 adds only `web_ai_agent_run` metadata. `reserveRequest` uses its existing `BEGIN IMMEDIATE` transaction to create/advance the run together with the per-generation reservation. `runId` is globally unique and bound to user and document IDs, a SHA-256 hash of the immutable original instruction/language/legacy history, and the first currency/per-generation quote, which must equal the authoritative server reservation at step 0. No original instruction, document body or tool output is stored. Document version/text and newly minted targets may change as edits execute; the bound original scope and quote may not.

Only a new run's step 0 is accepted; existing runs must present the exact next step and unchanged binding. Steps are 0 through 3, cumulative reservations cannot exceed four times the first quote, and new reservations stop at the persisted ten-minute expiry. The previous request must be settled. Each successful reservation commit consumes one generation attempt, regardless of subsequent provider rejection, disconnect or failure. A failed debit rolls back both run advancement and reservation. Reusing a request ID retains its existing duplicate/conflict handling; a new request ID cannot reset step 0 or replay a consumed step. Released or usage-pending generations permanently stop their run. Account deletion tombstones run user IDs with their existing request/ledger records.

Shared tool descriptions explicitly require distinct, non-overlapping targets within a batch. Replacing and formatting the same text requires a fresh target in a subsequent tool call. Regression tests cover run replay/skip/scope/quote/user/file boundaries, no-debit rejection, reopening the persisted database, failed-debit rollback, stopped/expired runs, four paid steps, and account deletion metadata retention.
